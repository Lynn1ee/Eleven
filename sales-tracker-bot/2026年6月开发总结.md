# Sales Tracker Bot — 2026年6月开发总结

## 1. 概述

6月工作围绕**系统稳定性**和**运维自动化**展开。5月底 bot 已具备完整业务功能（智能登记、跨月查询、报表卡片、定时提醒），但在实际运行中暴露出网络环境不稳定、进程意外退出、断连消息丢失等问题。6月工作重点从"功能开发"转向"生产可靠性"，交付了自愈系统、双通道架构、断连补录、月度归档、Windows 自动化部署等核心能力。

**项目运行环境**：Windows 10 Pro，Python 3.12，飞书开放平台

## 2. 架构升级：WebSocket + Webhook 双通道

### 背景

5月版本使用纯 WebSocket 长连接接收飞书事件。在 ngrok 隧道断连时，飞书无法推送事件，导致消息丢失。

### 方案

新增 Flask + ngrok Webhook 作为第二通道，与 WebSocket 并行运行：

- 保留原有 WebSocket 长连接（低延迟）
- 新增 HTTP Webhook 端点（`POST /webhook`），由 Flask + Waitress 生产服务器承载
- 通过 pyngrok 自动创建公网隧道，飞书事件同时推送到两条通道
- `feishu_client.py` 合并入 `server.py`，减少文件碎片

### 关键技术点

- ngrok 隧道自动检测与复用（避免 ERR_NGROK_334 重复启动错误）
- 3 次重试 + 已有进程检测机制
- 启动时清除系统代理变量，避免 Clash/V2Ray 等代理软件干扰飞书 API 连接

## 3. 自愈系统：Watchdog 守护进程

### 背景

线上多次出现 bot 进程崩溃、ngrok 隧道断连、WebSocket 无消息等问题，且无人值守时段无法及时恢复。

### 方案

开发独立的 `watchdog.py` 守护进程（~400 行），提供三层健康检测和自动恢复：

| 检测项 | 方法 | 判定标准 |
|--------|------|----------|
| 本地端口 | `POST /webhook` 探测 | 有无响应 |
| ngrok 隧道 | ngrok API 公网 URL | 公网可达性 |
| WebSocket 存活 | bot 写入的 `.last_msg_ts` | 4 小时内无消息（仅 08:00-23:00 时段） |

### 自愈流程

1. 检测到异常 → 杀掉 bot 进程 → 重新启动
2. 退避算法：连续失败则增加等待时间（2min → 5min → 15min → 30min）
3. 每次恢复成功/失败均推送飞书群通知
4. PID 文件锁防止重复启动
5. 短轮询模式（每 60 秒唤醒一次），避免长时间 sleep 导致假死

### 代码结构

```
watchdog.py
├── check_local_port()    # 本地 HTTP 探测
├── check_ngrok()         # 公网可达性
├── check_ws_alive()      # WebSocket 消息活性
├── get_bot_status()      # 综合判定 → healthy / dead / ngrok_down / ws_dead
├── kill_processes()      # 清理 bot 进程（排除自身）
├── start_bot()           # 后台启动 + 等待就绪
└── run_check()           # 单次检查 + 自愈 + 通知
```

## 4. 断连消息补录

### 背景

bot 重启期间的群聊消息会永久丢失。

### 方案

bot 启动后自动拉取飞书历史消息进行补录：

- 通过飞书 `im/v1/messages` API 拉取每个已知群聊的历史消息
- 记录每个群聊的最后补录时间戳（`.backfill_state.json`），重启后从断点拉取
- 可配置补录窗口：默认 6 小时，最大 24 小时（环境变量 `BACKFILL_WINDOW_MINUTES` / `BACKFILL_MAX_WINDOW_MINUTES`）
- 补录过程中对消息做与实时处理相同的分类、去重、登记流程
- 补录结束后发送摘要到群聊（如"断连补录完成：IM会话量 3 条"）

## 5. 月度 Base 自动归档

### 背景

5月方案中需要每月手动创建新 Base 和表格。

### 方案

实现完全自动化的月度归档：

- 每月首次运行时自动创建当月 Base（命名：`YYYY-MM 业务任务量`）+ 两张数据表
- 从上月 Base 中自动迁移当月 1 日的数据（避免跨月查询遗漏）
- 状态文件命名规则 `.state_YYYY-MM.json`，天然支持跨月查询
- 迁移后从旧 Base 删除已迁移记录（分批，每批 ≤500 条，符合飞书 API 限制）

## 6. Windows 环境自动化部署

### 背景

bot 部署在 Windows 10 个人电脑上，电脑重启后需要人工重新启动；watchdog 自身中途异常退出后无人拉回。

### 方案

两层守护机制确保系统始终运行：

| 层级 | 方式 | 触发条件 | 作用 |
|------|------|----------|------|
| 第 1 层 | 启动文件夹快捷方式 → `start_watchdog.bat` | 用户登录 | 电脑重启后自动拉起 |
| 第 2 层 | Windows 计划任务 → `health_check.py` | 每 10 分钟 | watchdog 中途死掉也能恢复 |

- `health_check.py` 通过读取 watchdog 心跳文件（`.watchdog_heartbeat`）判断存活，10 分钟无心跳则拉起
- 使用 `pythonw.exe` 静默执行，无命令行窗口、不闪屏
- 计划任务通过 `schtasks` 创建，无需管理员权限

完整守护链路：
```
计划任务(每10分钟) → 检查 watchdog 心跳 → 死了就拉起
watchdog(每30分钟)  → 检查 bot 健康      → 死了就拉起
bot                 → 处理业务            → 补录遗漏消息
```

## 7. 其他改进

### ngrok 管理优化
- 启动时检测已有 ngrok 进程，复用隧道避免 ERR_NGROK_334
- 清理残留僵尸 ngrok 进程（双进程冲突会影响隧道稳定性）
- 隧道 API 检测失败时优雅降级（bot 仍可启动，只是缺少 webhook 通道）

### 新增群聊自动发现
- 收到消息时自动将新群聊 ID 持久化到 `.chat_ids.json`
- 补录和定时提醒自动覆盖所有已知群聊
- 6月运行中自动发现并接管了第 2 个群聊

### 代码清理
- 删除过时文件：`pomodoro.py`、`proxy_server.py`、`ticket-refund-explainer.html`
- `feishu_client.py` 合并入 `server.py`，消除跨文件依赖
