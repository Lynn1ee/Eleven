# 飞书客服业务任务量登记机器人 — 开发过程总结报告

## 1. 项目概述

**项目名称**：Sales Tracker Bot（飞书客服业务任务量登记机器人）

**开发目标**：构建一个飞书群机器人，支持客服人员通过自然语言在群内登记日常业务任务量（IM 会话量、订单处理量），自动写入飞书多维表格（Bitable），并支持数据查询、报表生成和定时提醒。

**项目周期**：2026 年 5 月启动，持续迭代，长期使用

**运行环境**：Windows 10 Pro，Python 3.12

---

## 2. 技术架构

### 2.1 技术选型

| 层面 | 选型 | 原因 |
|---|---|---|
| 通信模式 | WebSocket 长连接 | 无需公网 URL、无需 ngrok 内网穿透，适合内网部署 |
| SDK | `lark-oapi` v1.6.6 | 官方 SDK，内置 WS Client 和事件分发器 |
| HTTP 请求 | `requests` | 轻量、成熟，用于直接调用飞书 OpenAPI |
| 数据存储 | 飞书多维表格 (Bitable) | 无需自建数据库，数据可视化方便 |
| 消息分类 | 正则表达式 | 轻量，无需引入 NLP 库 |
| 配置管理 | `python-dotenv` | 环境变量隔离敏感信息 |

### 2.4 核心模块

- **FeishuClient**：封装飞书 OpenAPI 调用，包括 Token 管理（自动续期）、用户姓名查询、消息发送/引用回复、Bitable 记录增删查
- **MessageHandler**：业务逻辑引擎，消息去重、登记分发、查询汇总、报表生成、定时提醒
- **run_scheduler**：后台线程，每日 14:55 和 23:55 触发数据上报提醒
- **create_event_handler**：SDK 事件回调，消息接收 → 去重 → 姓名解析 → 业务分发 → 引用回复

## 3. 核心功能

### 3.1 智能消息识别

通过正则表达式自动分类群聊消息：

- **表1（IM 会话量）**：识别"拼多多火车票 + 数字"等平台关键词，提取各平台会话数量
- **表2（订单登记）**：识别订单号格式（`HT001`、纯数字编号等），支持批量登记
- **查询**：个人汇总 / 当月排名 / 平台占比
- **报表**：日报 / 周报 / 月报，含各平台分类统计和排名
- **提醒**：手动查询上报情况 + 定时自动提醒

### 3.2 飞书多维表格

每月自动对应两张数据表：

- **表1 — IM会话量(拼多多+千牛+抖音)**：日期、姓名、拼多多火车票、拼多多机票、千牛、抖音、合计、备注
- **表2 — 火车票分销群聊登记表**：日期、姓名、订单号、备注

> 每月自动生成当月的新表，历史数据按月归档，支持跨月查询和对比。

### 3.3 用户名解析

三级优先级获取用户姓名：

1. `name_map.json` 自定义映射（跨租户外部用户）
2. 飞书通讯录 API（`contact/v3/users/{open_id}`）
3. 回退显示：`外部用户_xxxx`（41050 错误）或 `用户_xxxx`

### 3.4 消息去重

持久化消息 ID 到 `.processed_ids.json`，重启不丢失，防止重复登记。保留最近 5000 条记录。

### 3.5 引用回复

登记成功后使用飞书 `reply_message` API 引用原始消息，确保上下文清晰。

## 4. 遇到的关键问题与解决方案

### 4.1 跨租户外部用户姓名无法获取

**问题**：企业群内的外部用户（跨租户），飞书通讯录 API 返回 41050 错误（"no user authority error"），无法获取姓名。尝试开通 `contact:external_contact:readonly` 权限未找到。

**解决**：设计 `name_map.json` 手动映射机制 + `查ID` 命令快速获取 `open_id`。用户只需在 JSON 文件添加 `"<open_id>": "<姓名>"` 即可，bot 每次调用均实时读取，无需重启。

### 4.2 中文姓名编码乱码（"李玲" → "鏉庣幉"）

**问题**：姓名从 `name_map.json` 读取后写入飞书多维表格，正确的中文 "李玲" 被存储为乱码 "鏉庣幉"。经诊断确认：UTF-8 字节 `e69d8ee78eb2` ("李玲") 被当作 GBK 解码，产生了错误的字符 "鏉庣幉"。

**排查过程**：
- 排查 `name_map.json` 文件编码 → 正确 UTF-8
- 排查 `json.loads()` 解析 → codepoints 正确
- 排查 `json.dumps()` 序列化 → `\uXXXX` 转义正确
- 排查 HTTP 请求实际字节 → `requests` 发送正确
- 单独测试 API 写入 → 确认 API 本身正常

**最终方案**：修改 `add_records` 方法，将 `json=body`（依赖 `ensure_ascii=True` 生成 `\uXXXX` 转义）改为 `data=json.dumps(body, ensure_ascii=False).encode("utf-8")`（显式 UTF-8 字节），彻底避免编码转换环节的潜在问题。

### 4.3 @提及被识别为订单号

**问题**：消息中的 `@_user_1` 等 @提及被 `extract_table2_data` 当作订单号登记。

**解决**：在 `extract_table2_data` 中增加过滤逻辑，跳过以 `@` 开头的字符串。

### 4.4 机器人重复回复 / 重启后重复登记

**问题**：消息去重使用内存 `set`，重启后丢失，导致历史消息被重新处理。

**解决**：改为持久化到 `.processed_ids.json` 文件，最多保留 5000 条，每次处理前检查、处理后写入。

### 4.5 飞书多维表格字段缺失

**问题**：初始表格只有 "ID" 字段（类型 1005），缺少业务需要的 8 个自定义字段。

**解决**：通过飞书 `POST /bitable/v1/apps/{app_token}/tables/{table_id}/fields` API 逐个添加字段（类型 1=文本、2=数字、5=日期时间）。

### 4.6 Windows GBK 终端乱码

**问题**：Windows 终端默认 GBK 编码，Python 输出的中文字符全部显示为乱码，但不影响 Python 内部字符串处理和 HTTP 通信。

**处理**：接受终端显示乱码（不影响功能），通过写入 `sys.stderr` 的 hex 值进行编码调试。
