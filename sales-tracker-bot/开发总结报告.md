# 飞书客服业务任务量登记机器人 — 开发总结报告

## 1. 项目概述

**项目名称**：Sales Tracker Bot（飞书客服业务任务量登记机器人）

**开发目标**：构建一个飞书群机器人，支持客服人员通过自然语言在群内登记日常业务任务量（IM 会话量、订单处理量），自动写入飞书多维表格（Bitable），并支持数据查询、删除、定时提醒，以及含数据分析和可视化图表的日报/周报/月报（飞书互动卡片形式）。

**项目周期**：2026 年 5 月启动，持续迭代

**运行环境**：Windows 10 Pro，Python 3.12

## 2. 技术架构

### 2.1 技术选型

| 层面 | 选型 | 原因 |
|---|---|---|
| 通信模式 | WebSocket 长连接 | 无需公网 URL、无需 ngrok 内网穿透，适合内网部署 |

| 消息分类 | 正则表达式 | 轻量，无需引入 NLP 库 |

| 卡片消息 | 飞书卡片 JSON 2.0 | 图表内嵌、样式丰富、支持交互 |
| 配置管理 | `python-dotenv` | 环境变量隔离敏感信息 |

## 3. 核心功能

### 3.1 智能消息识别与路由

`classify_message()` 按优先级分 7 类：

| 优先级 | 类型 | 触发条件 | 示例 |
|--------|------|----------|------|
| 1 | 报表 | "日报"/"周报"/"月报" | `日报` |
| 2 | 提醒 | "提醒"/"催一下"/"上报" | `催一下数据` |
| 3 | 删除 | "删除"/"删掉"/"去掉" | `删除 HT001` |
| 4 | 查询 | "查询"/"排名" | `查询李玲`、`排名` |
| 5 | 会话登记 | 平台关键词 + 数字 | `拼多多火车票3000 千牛2000` |
| 6 | 订单登记 | HT 开头或纯数字 6 位+ | `HT001, HT002, HT003` |
| 7 | 未知 | — | 返回帮助文本 |

### 3.2 数据登记

- **表1（IM 会话量）**：正则提取拼多多火车票/机票、千牛、抖音四个平台的数值，自动计算合计
- **表2（订单号）**：支持逗号/空格/换行/顿号分隔，过滤 @提及，批量写入
- 去重：消息 ID 持久化，重启不丢失

### 3.3 跨月查询

- **个人查询**：汇总全部历史月份数据，按月份展示各平台明细。智能提取消息中的目标姓名（如"查询李玲"→查李玲），无指定目标时默认查发送者本人
- **带排名查询**：支持"李玲的排名"格式，同时展示个人汇总和全局排名位置
- **全员排名**：全部历史数据按合计排序，TOP3 金银铜牌
- 通过扫描 `.state_*.json` 文件实现跨月聚合

### 3.4 删除

- **引用删除**：引用此前登记消息回复"删除"，自动删除发送者当天的所有登记记录
- **关键词删除**：`删除 HT001`，模糊搜索后按表分组，调用飞书批量删除 API

### 3.5 定时提醒

后台线程每 30 秒检查，每日 **14:55**（白班结束）和 **23:55**（晚班结束）自动向所有已知群聊发送上报提醒。

### 3.6 报表系统（飞书互动卡片）

日报、周报、月报均以**飞书互动卡片（JSON 2.0）**形式返回，数据以 Markdown 原生表格 + 可视化图表内嵌在卡片中，清晰规整。

#### 日报
- 昨日每人各平台会话量（Markdown 原生表格）+ 订单数（Markdown 原生表格）
- 平台合计
- **7 天趋势折线图**（标注最高/最低点）
- 卡片 header：蓝色

#### 周报
- 上周每人汇总（Markdown 原生表格，含排名和日均）
- 平台合计
- **环比变化率**（与上上周对比，↑X% / ↓X% / →持平）
- **排名柱状图**（TOP10，前三名金银铜高亮）
- **平台占比饼图**
- 订单汇总（Markdown 原生表格）
- 卡片 header：青绿色

#### 月报
- 上月每人汇总（Markdown 原生表格，含排名和日均）
- 平台合计 + 占比百分比
- **环比变化率**（与上上月对比）
- **排名柱状图**（TOP10）
- **平台占比饼图**
- **每日趋势折线图**（当月每天会话量变化）
- 订单汇总（Markdown 原生表格）
- 卡片 header：紫色

#### 卡片消息降级机制
卡片 API 调用失败时自动降级：
1. 先尝试发送卡片消息
2. 若失败，发送文本 fallback + 单独图片消息

### 3.7 用户名解析

三级优先级获取用户真实姓名：
1. `name_map.json` 手动映射（跨租户外部用户，热加载无需重启）
2. 飞书通讯录 API（`contact/v3/users/{open_id}`）
3. 降级显示：外部用户（41050 错误）→ `外部用户_{open_id后4位}`，其他 → `用户_{open_id后4位}`

## 4. 遇到的关键问题与解决方案

### 4.1 中文姓名编码乱码

**问题**：姓名写入飞书多维表格后正确的中文变成乱码（"李玲" → "鏉庣幉"）。诊断确认 UTF-8 字节被当作其他编码解码。

**解决**：`add_records` 改为显式 UTF-8 编码：
```python
data=json.dumps(body, ensure_ascii=False).encode("utf-8")
```

### 4.2 跨租户外部用户姓名无法获取

**问题**：外部用户调用通讯录 API 返回 41050 错误（无权限），无法获取姓名。

**解决**：设计 `name_map.json` 手动映射 + `查ID` 命令快速获取 open_id，映射文件热加载。

### 4.3 飞书卡片消息格式验证

**问题**：卡片 JSON 格式错误导致 API 返回 `230099` 错误。
- `"size": "stretch"` → 不支持 → 改为 `"scale_type": "fit_horizontal"`
- `"tag": "note"` → Schema V2 不支持 → 改为 `"tag": "markdown"` 模拟

**解决**：逐一对照飞书卡片文档修正字段，添加降级 fallback 机制。

### 4.4 跨月报表数据不完整

**问题**：报表只查询当月数据，跨月范围内的历史数据丢失。

**解决**：新增 `_search_all_states()` 方法，扫描全部 `.state_*.json` 归档文件，跨月聚合查询。

### 4.5 多表删除 API 限制

**问题**：飞书批量删除 API 要求同批记录必须在同一张表中。

**解决**：`handle_delete()` 先按 `table_id` 分组，再对每组分别调用 `delete_records`。

### 4.6 消息去重重启丢失

**问题**：去重使用内存 `set`，重启后丢失导致历史消息被重复处理。

**解决**：持久化到 `.processed_ids.json`，保留最近 5000 条。

### 4.7 @提及被误识别为订单号

**问题**：`@_user_1` 等 @提及被当作订单号登记。

**解决**：在 `extract_table2_data` 中过滤以 `@` 开头的字符串。

### 4.8 引用回复消息识别失败

**问题**：用户通过飞书"引用回复"功能发送消息时，原始文本会附带 `回复 XXX: \n` 前缀和 `@提及`（如 `回复 李玲: \n占比 @数记君`），导致 `classify_message()` 无法匹配关键词，返回"未识别"帮助文本。

**解决**：在 `on_message_receive()` 中先清洗消息文本，用正则去掉 `回复 XXX:` 前缀和 `@\S+` 提及，再送入分类器。
